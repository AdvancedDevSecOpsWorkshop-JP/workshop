= DevSecOps with OpenShift Platform Plus (60 mins)

[#introduction]
== Introduction

このセクションでは、OpenShift Platform Plus (OPP) を使って、開発から本番までの全プロセスを通じて Software Supply Chain Security を重視した、包括的な DevSecOps ワークフローをどのように実現できるかを紹介します。

DevSecOps は Development、Security、Operations の略で、DevOps の実践に「継続的なセキュリティ」を組み込むための包括的なアプローチです。
本例では、セキュリティゲートを備えた CI/CD pipelines の定義、image scanning と signing、Trusted registry への安全な保管、そして高度なセキュリティ監視とアラートを備えたセキュアなクラスターへのデプロイといった機能を取り上げます。

それでは、Globex という e-commerce アプリケーションをデプロイする DevSecOps pipeline に関わるコンポーネント全体を確認していきましょう。

*Build-sign-image*. Tekton Chains によるセキュリティ強化

この task は、ソースコード (コミット済みの変更を含む) から container image をビルドします。
完了後、ビルドされた container image は、新しいタグと生成された Software Bill of Materials (SBOM) とともに、プライベートな quay registry に push されます。
SBOM とは、ソフトウェアソリューションのビルドに使用／必要となるコンポーネント（モジュールやライブラリを含む）を、機械可読で形式的に構造化した「完全な一覧」です。
平たく言うと、サードパーティの商用ツールやオープンソースソフトウェアを使って構築されたアプリケーションが「何でできているか」を可視化するものです。

この task はさらに Tekton Chains も使用します。
Tekton Chains は Kubernetes Custom Resource Definition (CRD) controller であり、OpenShift Pipelines におけるサプライチェーンセキュリティを強化するうえで重要な役割を担います。
task run を自動的に署名できること、そして in-toto のような高度な attestation (認証) 形式を採用していることにより、プロセスに対する信頼性と検証性がより高まります。

またこの task は、重要な TaskResults として IMAGE_URL と IMAGE_DIGEST を出力します。
これらのパラメータは、Tekton Chains が container image のデジタル署名を作成するトリガーとなるため非常に重要です。

続いて、以下の tasks を見ていきましょう。

image::/devsecops/pipeline-group3.png[]

*acs-image-check*. この task は roxctl CLI を使い、image に対してセキュリティポリシーの「ビルド時違反」をチェックします。このデモでは、container image の署名検証を行うポリシーを設定しています。ポリシーが有効で、image が未署名、または信頼されていない source による署名であれば pipeline は失敗します。署名が存在し、信頼できるものであれば、この task は成功します。

*acs-image-scan*. acs-image-scan は roxctl CLI を使い、image 内のコンポーネントと脆弱性を抽出します。image に含まれるパッケージに脆弱性がある場合、それらがレポートされます。

*scan-export-sbom*. この task は、SBOM に含まれる脆弱性をスキャンし、SBOM を外部からアクセス可能なリポジトリへエクスポートします。スキャンには、container images と filesystems 向けの vulnerability scanner であるサードパーティツール Grype を使用します。

以上です！
これで、OpenShift Pipelines (Tekton Chains) と Red Hat Advanced Cluster Security (Red Hat ACS) を利用して、Trusted Software Supply Chain (または DevSecOps アプローチ) を実現するセキュリティ機能について理解が深まったはずです。

[NOTE]
このワークショップでは Continuous Integration (CI) に OpenShift Pipelines を使用していますが、GitHub Actions、GitLab、Jenkins などの CI ツールでも、同様に Red Hat の各技術と連携してこれらの機能を実現できます。
実際に `oc get task <task-name> -o yaml -n {user}-cicd` を実行すると、task は単に bash script を実行しているだけであることがわかります。

[#trusted-image-registry]
== Trusted Image Registry

Red Hat Quay は、信頼できる geo-replicated かつセキュリティ機能を備えた container registry です。
container image の脆弱性スキャンができるだけでなく、署名済み image を SBOM ファイルや署名などの metadata とともに保存できます。
これらの資産は、前の pipeline のように、後段の pipeline で検証 (verification) や妥当性確認 (validation) に利用できます。

それでは Quay 上の container image を確認し、pipeline によって署名されていることを検証しましょう。

[#validating-signatures]
== Validating Signatures

=== Manual Verification

sigstore のユーティリティ `cosign` を使って image 署名を検証できます。
検証方法はいくつかありますが、まずは公開鍵を使って手動で検証してみます。

Tekton Chains が image に署名する際に使用した cosign signature は `openshift-pipelines` namespace に保存されていますが、
pipeline での検証を支援するため、署名のコピーが `{user}-cicd` namespace にも用意されています。

署名を確認するには、以下を実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get secret cosign-secret -o yaml -n {user}-cicd | oc neat
----

以下のような出力が表示されます。

[source,yaml,subs="+macros,attributes+"]
----
include::ROOT:example$globex-ui/templates/secret-cosign.yaml[]
----

secret には 3つの key がある点に注目してください。
`cosign.key` は image 署名に使う秘密鍵、`cosign.pub` は検証に使う公開鍵、`cosign.password` はパスワード用の key です。
値は Kubernetes 標準の慣習どおり base64 エンコードされています。

[NOTE]
image の検証には公開鍵のみが必要です。ここでは説明のために secret 全体のコピーを含めています。通常は秘密鍵とパスワードへのアクセスは厳格に制限することを強く推奨します。

検証に使用する公開鍵をローカルに取得するため、次を実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get secret cosign-secret -o jsonpath="{.data['cosign\.pub']}" -n {user}-cicd | base64 -d > ~/cosign.pub
----

取得できたことを確認するため、ファイルを表示します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
cat ~/cosign.pub
----

[source,yaml,subs="+macros,attributes+"]
----
-----BEGIN PUBLIC KEY-----
MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAEjWno6IupPFSRi9btNhFtMeS1iQbM
gN6OWsfUdhfT5TCf23ESE3vfuMWtX9syvjmemuGpZ+/fRDOyqAbVnAGNpQ==
-----END PUBLIC KEY-----
----

最後に `cosign` コマンドで Quay image registry 上の image を検証します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
cosign verify --insecure-ignore-tlog=true --key ~/cosign.pub registry-quay-quay-operator.{subdomain}/workshop{usernum}/globex-ui:main-b183894cabd3eebaa5844143d5ac60dc9863fb57
----

[NOTE]
`--insecure-ignore-tlog=true` は、cosign が public transparency log のチェックをバイパスするためのオプションです。Tekton Chains は、public instance ではなくワークショップクラスター上の transparency log を使うよう設定されているため、署名は cosign がデフォルトで参照する public transparency log にはアップロードされません。このオプションがないと検証は失敗します。

[source,bash,subs="+macros,attributes+"]
----
WARNING: Skipping tlog verification is an insecure practice that lacks of transparency and auditability verification for the signature.

Verification for registry-quay-quay-operator.{subdomain}/workshop{usernum}/globex-ui:main-b183894cabd3eebaa5844143d5ac60dc9863fb57 --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - The signatures were verified against the specified public key

[{"critical":{"identity":{"docker-reference":"registry-quay-quay-operator.{subdomain}/workshop{usernum}/globex-ui"},"image":{"docker-manifest-digest":"sha256:137f2141572bb833987dc04b58f4114d09e7a5d97d55b78ec8d064252d3f1020"},"type":"cosign container image signature"},"optional":null}]
----

[NOTE]
最後の json 出力にある `critical` は「重要情報」を示しているだけで、エラーを意味するものではありません。

=== Verifying With a Transparency Log

link:https://developers.redhat.com/products/trusted-artifact-signer/overview[Red Hat Trusted Artifact Signer (RHTAS),window=”_blank”] は、image signing を支援するツール群を提供します。
これらは主に upstream の link:https://www.sigstore.dev[Sigstore,window=”_blank”] プロジェクト由来で、以下を含みます。

* *Certificate Transparency Log*: 署名イベントを記録する、恒久的かつ改ざん不可能な台帳（ledger）／記録システムです。ログは公開されず、変更の影響を受けません。アーティファクトの完全性・真正性について判断するため、特定エントリの検証や取得などに利用できます。
* *Certificate Authority*:  認可された identity に対して短命（short-lived）な一時証明書を発行し、それを transparency log に公開する root certification authority です。第三者の key management system に保持された、既存の自己管理鍵を利用する選択肢も提供します。
* *Sigstore Clients*: 先ほど使用した `cosign` のような CLI ユーティリティに加え、ソースコード、artifacts、SBOM、container images のデジタル署名の生成・検証に使う各種ツールを含みます。

本ワークショップでは、RHTAS がクラスターにデプロイされており、Tekton Chains は透明性ログで署名を検証できるよう必要な metadata を自動的にアップロードするよう設定されています。

まず、cosign が transparency log を使って検証できるよう、環境変数を設定します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
export TUF_URL=https://tuf-trusted-artifact-signer.{subdomain}
export COSIGN_FULCIO_URL=https://fulcio-server-trusted-artifact-signer.{subdomain}
export COSIGN_REKOR_URL=https://rekor-server-trusted-artifact-signer.{subdomain}
export COSIGN_MIRROR=$TUF_URL
export COSIGN_ROOT=$TUF_URL/root.json
export COSIGN_YES="true"
export SIGSTORE_FULCIO_URL=$COSIGN_FULCIO_URL
export SIGSTORE_REKOR_URL=$COSIGN_REKOR_URL
export REKOR_REKOR_SERVER=$COSIGN_REKOR_URL
----

次に、cosign の初期化と設定を行い、transparency log による検証に必要な Sigstore コンポーネントから証明書を取得します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
cosign initialize
----

最後に、以下のコマンドで検証を実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
cosign verify --key ~/cosign.pub registry-quay-quay-operator.{subdomain}/workshop{usernum}/globex-ui:main-b183894cabd3eebaa5844143d5ac60dc9863fb57
----

[source,bash,subs="+macros,attributes+"]
----
Verification for registry-quay-quay-operator.apps.{subdomain}/workshop{usernum}/globex-ui:main-b183894cabd3eebaa5844143d5ac60dc9863fb57 --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - Existence of the claims in the transparency log was verified offline
  - The signatures were verified against the specified public key

[{"critical":{"identity":{"docker-reference":"registry-quay-quay-operator.{subdomain}/workshop{usernum}/globex-ui"},"image":{"docker-manifest-digest":"sha256:137f2141572bb833987dc04b58f4114d09e7a5d97d55b78ec8d064252d3f1020"},"type":"cosign container image signature"},"optional":null}]
----

この実行では、先ほどは行っていなかった「transparency log 上で署名が存在することの検証」が行われている点に注目してください。

[#deploying-web-application-gitops]
== Deploying Web Application

=== Using overlays and Kustomize in the DevSecOps pipeline

複数の環境へアプリケーションをデプロイする際の一般的なパターンとして、以下のような構造を持つリポジトリを用意します。

* *base*: the common assets that we want to deploy
* *overlays*:
    ** *dev*: 「dev」環境向けに base の値を上書きする値
    ** *prod*: 「prod」環境向けに base の値を上書きする値

以前と同様に ApplicationSet を使ってアプリケーションをデプロイしますが、今回は git generator を使用します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
sed 's/$USER/{user}/' ~/workshop/content/modules/ROOT/examples/web-nodejs-appset.yaml | sed 's/$SUBDOMAIN/{subdomain}/' | oc apply -f - -n {user}-argocd
----

新しく作成した ApplicationSet を簡単に確認します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get appset web-nodejs -o yaml -n {user}-argocd | oc neat
----

[.console-output]
[source,yaml,subs="attributes+,+macros"]
----
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: web-nodejs
  namespace: {user}-argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io <1>
spec:
  generators:
  - git: <1>
      directories:
      - path: globex/overlays/* <2>
      repoURL: https://gitea-gitea.{subdomain}/{user}/gitops.git <3>
      revision: HEAD
      values:
        user: {user} <4>
  goTemplate: true
  goTemplateOptions:
  - missingkey=error
  template:
    metadata:
      name: app-{{.path.basename}} <5>
      namespace: '{{ .values.user }}-argocd'
    spec:
      destination:
        name: in-cluster
        namespace: '{{ .values.user }}-{{.path.basename}}'
      project: '{{ .values.user }}'
      source:
        kustomize:
          patches:
          - patch: |-
              - op: replace
                path: /spec/template/spec/containers/0/env/0/value
                value: 'gateway-vertx-{{ .values.user }}-{{.path.basename}}'
            target:
              kind: Deployment
              name: web-nodejs
        path: '{{.path.path}}' <6>
        repoURL: https://gitea-gitea.{subdomain}/{user}/gitops.git
        targetRevision: main
      syncPolicy:
        automated:
          prune: true
----
<1> git generator を使用し、対象リポジトリ／パス配下の各ディレクトリごとに Application を作成します
<2> 対象パス。ここ配下の各サブディレクトリを使って application を作成します (この例では `dev` と `prod` overlays)
<3> 対象リポジトリ
<4> template に渡す追加 values
<5> Application を生成する対象パスの basename (この例では `dev` または `prod`)
<6> 現在のディレクトリに対応する、リポジトリ内のフルパス

Applications が作成されたことを確認します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get apps -n {user}-argocd
----

[.console-output]
[source,yaml,subs="attributes+,+macros"]
----
app-dev              Synced        Healthy
app-prod             Synced        Progressing
coolstore-app-dev    Synced        Healthy
coolstore-app-prod   Synced        Healthy
dev-tools            Synced        Healthy
pipeline-helm        Synced        Healthy
----

[NOTE]
`app-prod` がしばらく `Progressing` のまま、または `Degraded` と表示されることがあります。
これは、本番環境に対して Pipeline が生成した更新 image をまだデプロイしていないためです。
このステップは次のセクションで実施します。

Shared OpenShift GitOps の Application タイルを見て、作成されたことを確認できます。

* OpenShift GitOps に移動し、トップページで "app-dev" application を選択して詳細を開きます。

=== Adopting a GitOps approach for deployments across multiple namespaces

アプリケーションアーキテクチャのセクションで述べたとおり、"Globex" アプリケーションは OpenShift GitOps を使って複数の namespaces や clusters にまたがってデプロイされます。

* Gitea の URL を開きます: link:https://gitea-gitea.{openshift_cluster_ingress_domain}[window="_blank"]

* 提供された認証情報でログインします: username: *{user}*, password: *openshift*.

=== Deploying to production using a Pull Request in Gitea

OpenShift GitOps の app-prod Application を使って、同じアプリケーションを "PROD" 環境にもデプロイしています。主な違いは、prod 側が production 用の値を含む "globex/overlays/prod" を使用している点です。

production へデプロイする際には、「手動承認（manual approval）」つまり「gating」を設けるのが一般的です。
ここでは Gitea の Pull Request を使って、"globex/overlays/prod" にある PROD manifests の変更を承認します。

pipeline 実行の最終ステップで Pull Request はすでに作成されているので、gitea で確認して merge し、GitOps により "{user}-prod" namespace へのデプロイを開始しましょう。

* Gitea を開き、*gitops* リポジトリを選択し、以下のように *Pull Requests* をクリックします。

image::/devsecops/gitea-pull-request.png[]

Pull Request をクリックし、「Create Merge Commit」をクリックしてから create commit を選択します。

image::/devsecops/gitea-merge-commit.png[]

* Pull Request の詳細で *Files Changed* をクリックすると、以下のように prod 環境向けの image 参照が更新されていることが確認できます。

image::/devsecops/gitea-merge-changes.png[]

* application details ウィンドウを閉じ、application ページで、OpenShift GitOps がターゲット cluster / namespace にデプロイした Kubernetes リソース（deployments、services など）を確認します。

[NOTE]
Argo CD が変更を検知するまで数分かかる場合があります。Shared インスタンスで `app-prod` Application の `Refresh` ボタンをクリックすると処理を早められます。

== Using Security Policies in Red Hat Advanced Cluster Security (Red Hat ACS)

=== Review Trusted Signature Policy

* Red Hat ACS console を開きます: link:https://central-stackrox.{openshift_cluster_ingress_domain}[window="_blank"]

* 下図のように "Keycloak" auth provider を選択します。

image::/devsecops/acs-keycloak.png[]

* Keycloak でログインします: username *{user}* and password *{password}*.

* Red Hat ACS console に入ったら、左メニューから "Platform Configuration -> Policy Management" を選択します。policies ページが表示されます。

image::/devsecops/acs-policies.png[]

Red Hat ACS には、複数クラスター群（fleets of clusters）全体にわたるセキュリティベストプラクティスと保護策の実装を支援する、約 85 の out-of-the-box policies が用意されています。
リストをスクロールしていくつか確認できます。

* 次に "Trusted Image Signature" policy を見てみましょう。"Filter policies" で "Policy" と入力して Enter を押し、続いて "Trusted Signature" と入力します。

image::/devsecops/acs-trusted-signature-policy.png[]

* policy をクリックして詳細を確認します。

image::/devsecops/acs-trusted-signature-policy-details.png[]

"Policy details" セクションでは、metadata、Severity レベルなどの情報が定義されています。

image::/devsecops/acs-policy-details-section.png[]

"Policy Behavior" セクションでは、policy が「いつ」「どのように」適用されるかを定義できます。

image::/devsecops/acs-policy-behavior-section.png[]

"Lifecycle stages" では、Build、Deploy、Runtime のどの段階で適用するかを指定できます。この Policy では Build と Deploy が選択されています。

response method には2つのオプションがあります。

* *Inform*: policy はアラートを出すだけで強制（enforce）はしません。つまり具体的なアクションは取りません。
* *Inform and enforce*: policy はアラートを出しつつ強制します。例えば、ポリシー違反の container を削除する、または前の例のように trusted signature がないため pipeline を失敗させる、といった動作です。

最後に "Enforce" では、どのように強制するかを各オプションで制御できます。

ページ下部の Policy Scope セクションでは、対象 cluster や namespace を選択して policy のスコープを制御できます。ワイルドカードも利用でき、labels による選択も可能です。

* 次に "Policy Criteria" セクションの "View" をクリックし、署名検証がどう実装されているかを確認します。

image::/devsecops/acs-policy-criteria-section.png[]

* ポップアップで "cosign" をクリックすると、container image を検証するために使用される公開鍵署名へ移動します。これは、OpenShift Pipelines / Tekton Chains がビルド後に container images を署名する際に使用する秘密鍵署名と対になります。署名プロセスは次のセクションで詳しく説明します。

image::/devsecops/acs-signature-integration.png[]

=== Viewing Policy Violations

policy を確認したので、この policy に関する違反（violations）を見てみましょう。

* 左サイドバーの `Violations` をクリックし、フィルタに `Trusted Signature Policy` を追加します。

image::/devsecops/acs-policy-violations.png[]

* `globex-ui` image を除き、他の images はこの policy に違反していることに気づくはずです。`globex-ui` は pipeline によってビルドされ、正しく署名が付与され検証済みだからです。

[NOTE]
他の namespaces の署名違反が表示されないのは、この Policy が `{user}-dev` と `{user}-prod` namespaces にスコープされているためです。
さらに ACS は multi-tenancy として構成されており、あなたのユーザーは許可された namespaces と clusters に由来するデータのみ閲覧できます。

=== Viewing Vulnerabilities

次に Red Hat ACS が、image vulnerabilities の確認を通じてクラスターセキュリティをどのように監視できるかを見ていきます。

* 左メニューで "Vulnerability Management -> Workloads CVEs" をクリックし、フィルタで Images を選択します。

image::/devsecops/acs-vuln-management2.png[]

* フィルタ欄に "Image" と入力して Enter、続けて "globex-ui:main" と入力し、ドロップダウンに出てきたものを選択します。

image::/devsecops/acs-image-cves2.png[]

上でハイライトされている `globex-ui:main` image をクリックすると、image details に移動します。
ここでは CVEs の一覧、components の一覧、そして (`Resources` タブで) この image を使用している deployments の一覧が確認できます。
たとえば image が侵害されたような状況で、影響範囲を把握し緩和策を講じるのに役立ちます。

image::/devsecops/acs-image-details2.png[]

[NOTE]
Red Hat Advanced Cluster Security には CVE 管理のワークフローがあり、修正がまだ利用できない場合などに特定 CVE の defer（延期）を申請できます。
その後、security または platform チームが必要に応じて承認／却下します。

以上です！
Red Hat ACS を使って、DevSecOps pipeline 内のセキュリティゲートとして利用できるセキュリティポリシーを定義し、trusted でない／望ましくないコンテンツが production 環境へ入ることを防ぎつつ、複数クラスターとアプリケーションのセキュリティを各環境で継続監視できることが理解できたはずです。

[NOTE]
Red Hat Advanced Cluster Security は multi-tenants として構成されており、各ユーザーは自分が管理する namespaces に関する情報のみ閲覧できます。
あなたの場合は `{user}-xxxx` namespaces です。そのため、他の参加者がデプロイした `globex-ui` image や deployments ではなく、自分に関連するものだけが表示されます。

== Summary

Here a quick summary of all you've seen in this lab:

* OpenShift Platform Plus は、マルチクラスター管理 (RH ACM。ラボでは未実施) 、継続的セキュリティ (Red Hat ACS) 、Trusted Registry (Red Hat Quay) を提供する包括的なソリューションであり、Trusted Software Supply Chain を実装して DevSecOps アプローチを採用するための優れた基盤になります。

* OpenShift Pipelines (Tekton ベース) は高度な CI/CD 機能を提供し、RH ACS と直接統合して DevSecOps を実現できます。また Tekton Chains controller による image signing などの高度な機能も提供します。

* OpenShift GitOps (ArgoCD ベース) により、開発から本番、さらにその中間段階も含め、複数環境・複数クラスターへアプリケーションをデプロイする GitOps アプローチを採用できます。

* Red Hat Advanced Cluster Security は、security policies や image scanning (脆弱性) などの out-of-the-box セキュリティ機能を提供し、全クラスターにわたる継続的なセキュリティ監視を実現します。
