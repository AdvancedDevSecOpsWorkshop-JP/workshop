= Advanced OpenShift GitOps(30 mins)

このモジュールでは、Platform チームが把握しておくべき、また Developers も理解しておくべき高度な GitOps トピックを確認します。
扱うトピックには、Argo CD Architecture、Command Line Interface、Role Based Access Controls (RBAC)、AppProjects、および任意の namespace 内のアプリ などが含まれます。

[#openshift-gitops-architecture]
== OpenShift GitOps Architecture

このセクションでは、以下の図に示す OpenShift GitOps のアーキテクチャを簡単に概観します。

image::gitops/argocd-architecture.png[]

[NOTE]
上記の図では、点線の内側に含まれるものはすべて OpenShift 上で稼働しており、点線の外側は外部依存（external dependencies）または外部との連携（interactions）を示しています。

OpenShift GitOps operator は、指定した namespace で稼働する Argo CD のインストールをデプロイ、管理、アップグレードするために使用されます。
Argo CD のインストールは複数のコンポーネントで構成され、それぞれが個別の deployment として稼働します。
主なコンポーネントは以下のとおりです。

1. *Application Controller*: Kubernetes リソースをデプロイし、リソースの変更を監視する責務を持ちます。そのために Kubernetes API とやり取りします。
2. *Repo Server*: git リポジトリ経由で manifests へのアクセスを管理し、manifests（例：yaml ファイル）を取得します。これらの manifests は、生の yaml、helm、kustomize から生成できます。また、プラグインアーキテクチャにより追加ツールも利用可能です。性能向上のため、生成された manifests を redis コンポーネントにキャッシュします。
3. *Server*: ユーザーインターフェースと REST API を提供します。
4. *Dex (optional)*: OpenShift OAuth2 経由の認証を提供します。本ワークショップでは Keycloak に対して直接認証しているため利用しません。
5. *ApplicationSet Controller (図示は無し)*: generator を使って Applications を生成する ApplicationSets を管理します。generator は Pull Requests、git 内のディレクトリ、クラスターなどに基づいて Applications を作成できます。

[#workshop-architecture]
== Workshop Architecture

このワークショップでは、以下の2つの GitOps インスタンスがデプロイされています。

1. *Cluster GitOps*: Platform チームがクラスター構成（cluster configuration）と、cluster-scoped なテナントリソース（例：Namespaces、Quotas、NetworkPolicy、Operators など）を管理するために使用します。クラスター構成を管理するために cluster-admin レベルの Kubernetes 権限を持ちます。

2. *Shared GitOps*: アプリケーションチームがアプリケーションをデプロイするために使用するインスタンスです。複数のアプリケーションチームが共用する GitOps 環境であるため、チーム間で他チームのアプリケーションを参照・変更できないよう、Argo CD Role Based Access Controls (RBAC) が構成されています。また、Cluster GitOps と比較すると Kubernetes 権限は大幅に少なくなっています。

=== Cluster GitOps

デフォルトでは OpenShift GitOps operator は `openshift-gitops` namespace にインスタンスをインストールします。
このインスタンスは cluster-scoped であり、テナントに代わって権限の強いリソース（Namespaces、Quotas、Operators など）を管理するなど、クラスター構成用途で利用することが推奨されています。

まず、このインスタンスを簡単に確認します。
OpenShift Application Menu にアクセスし、赤でハイライトされている Cluster Argo CD を選択します。

image::gitops/openshift-app-menu-cluster-argocd.png[]

このインスタンスの Argo CD UI が開きます。ログインするには、赤で示された Keycloak ボタンをクリックします。

image::gitops/argocd-keycloak-login.png[]

本ワークショップでは Keycloak による Single-Sign-On を利用しているため、すでに Keycloak で OpenShift にログイン済みであれば Argo CD にも自動的にログインされます。
ログイン後、以下のような applications が表示されます。

image::gitops/argocd-cluster-users.png[]

user1、user2、user3 など、すべてのユーザープロジェクトを閲覧できる点に注目してください。
これは Argo CD RBAC を使い、`developers` グループのユーザーに対して、これらの applications が紐づく Argo CD Project への限定的なアクセスを付与しているためです。

[NOTE]
cluster-scoped のインスタンスは通常 Platform チームが管理し、developers がアクセスすることは一般的ではありません。ここでは説明目的で提供しています。高い自律性を持つ開発チームにアクセスを許可する場合でも、通常はそのチームに固有の Applications のみに限定します（例：user1 は user1 の application だけ見える、など）。

自分のユーザーに対応する app（`{user}`）を選択してください。参加者が多い場合 Applications が多数あるため、フィルタバーを使って自分の application を探せます。

image::gitops/argocd-filter.png[]

Application を見つけたらクリックし、その Application がデプロイしたリソースを確認します。
この Application は、テナント（あなたのユーザー）がこのクラスターで必要とする namespace、rolebindings などを含む各種リソースをプロビジョニングしています。
これらは Platform チーム（cluster-admins）が開発チーム向けに用意すべきリソースです。

image::gitops/cluster-argocd-user-app.png[]

ログイン中ユーザーに関連付けられたグループは、ユーザーボタンをクリックすると確認できます。

image::gitops/argocd-user-groups.png[]

`developers` グループと、ユーザーが所属するユーザー固有のチーム（`teamX`）が表示される点に注意してください。
このシナリオでは user1 は team1、user2 は team2…という割り当てです。`developers` グループは、すべての application developers が所属する汎用グループです。

これらのグループは Keycloak でプロビジョニングされており、アプリケーションにログインした際に Argo CD でも利用できるようになります。

次のセクションでは Shared Argo CD インスタンスを確認し、その後 Argo CD RBAC がどのように構成されてユーザーのアクセス権限が決定されるかを深掘りします。
現時点では、`Users` project 内の Applications に対しては Get と Sync のみが有効であり、非常に限定的な権限しかない点を押さえてください。

[NOTE]
ここにはクラスター構成用途の別の Argo CD Project もデプロイされており、`developers` グループには権限がありません。
ワークショップ終了時に GitOps でワークショップクラスターがどのように構成されているか確認したい場合は、講師に可視化を依頼してください。

=== Shared GitOps

Shared GitOps インスタンスは、開発チーム（つまりあなた）がアプリケーションやリソースをデプロイするために操作するマルチテナントの Argo CD インスタンスです。
Cluster GitOps と比べ、開発チームの責務（アプリケーションのデプロイ）に合わせてクラスター上の権限が大幅に制限されています。

[NOTE]
技術的には、Argo CD RBAC を活用することで 1つの Argo CD インスタンスをクラスター構成と開発デプロイの両方に使うことも可能です。しかし privilege escalation の可能性を最小化するため、これらのユースケースは別インスタンスに分けることが推奨されます。たとえば Argo CD RBAC に穴があると、開発者がクラスター構成用途インスタンスの高い Kubernetes 権限を悪用できてしまう可能性があります。

OpenShift application menu から Shared GitOps インスタンスへのリンクを使ってログインします。

image::gitops/openshift-app-menu-shared-argocd.png[]

ログイン手順は Cluster GitOps と同じです。
Keycloak ログインボタンをクリックして完了してください。
ログイン後、Applications の一覧が表示されます。

image::gitops/shared-gitops-apps.png[]

Shared GitOps では、Cluster GitOps と異なり、自分のユーザーに紐づく Applications だけが表示される点に注目してください。

`dev-tools` Application と、前モジュールでデプロイした他の applications が表示されます。
`dev-tools` は、後続の Pipelines モジュールで使用するチーム固有の Sonarqube と Nexus インスタンスをデプロイするためのものです。
近くの参加者と見比べると、全員がそれぞれ固有の dev-tools Application を持っていることに気づくはずです。
同じ Argo CD インスタンス内で、同名の Application を複数持てるのはなぜでしょうか？

これを理解するため、次のセクションで Argo CD RBAC も含めて詳しく見ていきます。

== Argo CD Deep Dive

=== Argo CD CLI

ArgoCD CLI を使って Shared GitOps をより詳しく確認します。
`{user}-argocd` namespace には、Argo CD にログインするための認証情報を含む argocd-cli という secret が事前作成されています。

[NOTE]
通常、OIDC を使う Argo CD のログインは `--sso` スイッチを使い、localhost 上で OIDC コールバックを処理するローカル Web サーバーを起動します。
しかし、本ワークショップではターミナルが OpenShift 上の pod 内で動作しているため、この方法は使えません。
そこで、SSO ユーザーと同一権限を持つローカルアカウント `{user}-cli` を事前に作成しています。
通常、Argo CD のローカルアカウントはユーザー用途ではなく、オートメーション用途でのみ使用すべきです。

secret の値を環境変数としてターミナルに設定するため、以下のコマンドを実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
export ARGOCD_AUTH_TOKEN=$(oc get secret argocd-cli -n {user}-argocd -o jsonpath="{.data.ARGOCD_AUTH_TOKEN}" | base64 -d)
export ARGOCD_SERVER=$(oc get secret argocd-cli -n {user}-argocd -o jsonpath="{.data.ARGOCD_SERVER}" | base64 -d)
export ARGOCD_USERNAME=$(oc get secret argocd-cli -n {user}-argocd -o jsonpath="{.data.ARGOCD_USERNAME}" | base64 -d)
alias argocd='f(){ argocd "$@" --grpc-web;  unset -f f; }; f'
----

Argo CD CLI は指定した環境変数を自動的に利用するため、明示的な login は不要になります。
また最後の alias により、`argocd` コマンドを呼び出す際に `--grpc-web` が自動付与されます。
OpenShift Route を経由してコマンドを実行しているため、このパラメータにより不要な警告を避けられます。

[IMPORTANT]
ターミナルのインターフェースを再起動した場合、コマンドラインから Argo CD にアクセスするために、上記コマンドを再度実行する必要がある場合があります。

[source,sh,subs="attributes",role=execute]

----

=== Argo CD Projects

Argo CD の link:https://argo-cd.readthedocs.io/en/stable/user-guide/projects/[Projects,window=’_blank’] は、
Applications をグルーピングし、Applications や Project スコープの他リソースに対する権限を管理するために使われます。
用語は同じでも、Argo CD Project は OpenShift Project とは異なる点に注意してください。
OpenShift Project は Kubernetes の `kind: Project` で表現されますが、Argo CD Project は `kind: AppProject` で表現されます。

Argo CD のすべての Application は必ずいずれかの Project に紐づく必要があります。
特にマルチテナントの Argo CD を運用する場合、Project はユーザー権限を決めるだけでなく、その Project に紐づく Applications が「何をできるか」を制限できるため非常に有用です。
ドキュメントによれば Argo CD Project では次のことが可能です。

* デプロイ可能なものを制限 (信頼できる Git source repositories)
* デプロイ先を制限 (destination clusters と namespaces)
* デプロイ可能／不可能なオブジェクト種別を制限 (例：RBAC、CRDs、DaemonSets、NetworkPolicy など)
* project roles を定義して application RBAC を提供 (OIDC groups や JWT tokens に紐づけ)

[IMPORTANT]
Argo CD はインストール時に `default` project を含みますが、これを使用しないことが強く推奨されます。
管理者はユースケースに応じて必要な Projects を作成してください。

本ワークショップの Shared GitOps インスタンスでは、各ワークショップチーム（＝各ユーザー）ごとに独自の Project があり、Applications のアクセス権と制約を管理しています。
自分のチームの project を確認するには、以下を実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----

----

単一の project が表示されることに気づくはずです。

{user}  {user} project  5 destinations  *        <none>                      <none>                        <none>          disabled
----

[.console-input]
[source,sh,subs="attributes",role=execute]
----

----

[.console-output]
[source,bash,subs="attributes+,+macros"]

ユーザーの Applications は `{user}-*` namespace のみへデプロイできるよう、destination が制限されている点に注目してください。
この destination 制限により、たとえ Argo CD の application-controller 自体が他 namespace へデプロイできる権限を持っていても、この Project に属する Applications は他 namespace へはデプロイできません。

また、いくつかのリソース種別へのアクセスを拒否 (deny) している点にも注意してください。namespace を持たない cluster-scoped リソースはすべて拒否しています。
さらに、ResourceQuota や LimitRange のような namespace-scoped リソースも拒否しています。
これらは Platform チームの管掌で管理すべきリソースだからです。

最後に、clusters や repositories のような一部の Argo CD リソースは、グローバルまたは Project レベルでスコープ設定できます。
Project レベルでスコープさせることは、Argo CD 管理者が application チーム向けにセルフサービスを可能にしたい場合に有用です。
本ワークショップではこれらのリソースはグローバルで定義していますが、詳しくは Argo CD ドキュメントで詳細に解説されています。

link:https://argo-cd.readthedocs.io/en/stable/user-guide/projects/#project-scoped-repositories-and-clusters[Project scoped Repositories and Clusters,window="_blank"]

=== Role Based Access Control

Argo CD には、Kubernetes RBAC とは別に独立した Role Based Access Control (RBAC) があります。
ユーザーが Argo CD UI、CLI、API を通じて Argo CD とやり取りする場合は Argo CD RBAC が適用されます。
一方、OpenShift Console や `kubectl`/`oc` で Argo CD リソースを直接操作する場合は、Kubernetes RBAC のみが適用されます。

また、前述の GitOps Architecture で示したように、Argo CD の application-controller は Kubernetes API とやり取りし、その権限は Kubernetes RBAC によって制御されます。
つまり、Argo CD がデプロイ／管理できる Kubernetes リソースは、application-controller に Kubernetes RBAC で許可された範囲に限られます。

この関係は次の図で示されています。

image::gitops/argocd-rbac.png[]

Argo CD RBAC は link:https://casbin.org/docs/overview[Casbin, window=”_blank”] ライブラリで実装されています。
権限は role を作成して定義し、その role をグループまたは個別ユーザーに割り当てます。
Argo CD には標準で次の2つの role が含まれています。

* role:readonly - すべてのリソースに対する読み取り専用アクセス
* role:admin - すべてのリソースに対する無制限アクセス

roles と permissions は、グローバル設定と Project ごとの設定の2箇所で定義できます。
テナント向けの roles／permissions は Project 側で定義し、グローバル roles は Argo CD 管理者やグローバルスコープのリソース管理に限定することが強く推奨されます。

ワークショップ参加者（developer）であるあなたは、グローバル設定を見る権限はありませんが、設定内容は以下のようになっています。

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
  policy.csv: |
    p, role:none, *, *, */*, deny
    g, system:cluster-admins, role:admin
    g, cluster-admins, role:admin
    p, role:developers, clusters, get, *, allow
    p, role:developers, repositories, get, *, allow
    g, developers, role:developers
  policy.default: role:none
  scopes: '[accounts,groups,email]'
----

このグローバル設定についての注意点は以下です。

* 最初のセクションは policies で、roles と対応する groups を定義しています
** すべての権限を拒否する明示的な role `role:none` を定義しています
** `cluster-admins` グループのユーザーは `admin` role に割り当てられます
** 開発者向けに、clusters や repositories といったグローバルリソースへの read アクセスを付与する role を定義しています
** `developers` グループに `developers` role を割り当てています
* `policy.default` を `role:none` に設定し、デフォルトではアクセス拒否、必要な権限は明示的に許可する方式にしています
* scopes は accounts、groups、email を含むよう設定されています。Argo CD は OIDC で認証しており、ここで選択した OIDC link:https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims[scopes, window="_blank"] は policy のグループマッチングに利用されます

[IMPORTANT]
`policy.default` に与えた権限は、追加 role の `deny` で打ち消せません。そのため、ここでは権限を持たない role をデフォルトにしています。

[NOTE]
`policy.default` を空文字にして、`role:none` を定義するのと同等の効果を得ることも可能ですが、本ワークショップの作者は意図の混乱を避けるために、明示的に role を定義する方を好んでいます。

次に、あなたのチーム／ユーザー向けに用意された Project 内で定義されている RBAC を見てみましょう。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
argocd proj role list {user}
----

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
ROLE-NAME  DESCRIPTION
admin      TeamX admins
pipeline   Pipeline accounts
----

`admin` と `pipeline` の2つの role が定義されていることがわかります。
`admin` role は、この Project 内の Applications を管理するユーザー向けです。
`pipeline` role は自動化ツール向けで、後続モジュールで OpenShift Pipelines が利用します。

role の定義内容を確認します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
argocd proj role get {user} admin
----

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
Role Name:     admin
Description:   TeamX admins
Policies:
p, proj:{user}:admin, projects, get, {user}, allow
p, proj:{user}:admin, applications, *, {user}/*, allow
p, proj:{user}:admin, exec, create, {user}/*, allow
g, team1, proj:{user}:admin
g, user1-cli, proj:{user}:admin
p, proj:{user}:pipeline, projects, get, {user}, allow
p, proj:{user}:pipeline, applications, get, {user}/*, allow
p, proj:{user}:pipeline, applications, sync, {user}/*, allow
g, {user}-pipeline, proj:{user}:pipeline
----

role の情報 (policies など) が表示されます。
最初の policy を要素に分解して、どのように定義されているかを理解しましょう。

image::gitops/argocd-policy.png[]

1. `p` は policy の定義を意味し、role に権限を付与するために使います。
2. 次は、この policy が属する role です。この例では Project `{user}` にスコープされた admin role です。
3. 次は権限を付与する対象リソース種別で、ここでは projects です。applications や clusters など、さまざまな Argo CD リソースがサポートされています。 (link:https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/#rbac-resources-and-actions[参考, window="_blank"])
4. 次に action を指定します。ここでは get という単一 action です。link:https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/#rbac-resources-and-actions[様々なアクション, window="_blank"] が利用可能です。`*` を使うとすべての actions を意味します。
5. 次に対象となる具体的な Argo CD リソースを指定します。`*` のようなワイルドカードも可能ですし、この例のように `{user}` という名前で `{user}` Project を指定することもできます。Project にスコープされた Applications の場合は、後続行のように `<Project>/<Application>` 形式を使えます。
6. 最後に `許可 (allow)` か `拒否 (deny)` かを指定します。

policies によって role を定義したら、次にその role をグループへ割り当てます。
これは行頭が `g` で示されます。
例えば `g, teamX, proj:{user}:admin` は、Project スコープの `admin` role を `teamX` グループへ割り当てることを意味します。

どの属性を `group `として扱うかは、先ほど確認した `scope` 設定で制御されます。
通常は `groups` が最も一般的ですが、`email` のような scope を含めると、個別ユーザーに role を紐づけることもできます。
要点としては、`email` など追加した scope は、Argo CD のマッチング上 “group として扱われる” ということです。

先ほど述べたとおり、この基本的な project は閲覧権限のみが付与されており、変更や削除はできません。
確認のため、Project の削除を試してみます。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
argocd proj delete {user}
----

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
FATA[0000] rpc error: code = PermissionDenied desc = permission denied: projects, delete, user1, sub: user1-cli, iat: 2024-07-30T17:14:43Z
----

想定どおり、Project の削除権限がないため拒否されました。
繰り返しになりますが、Argo CD RBAC が適用されるのは Argo CD の UI / CLI 経由で操作した場合のみです。
もし Argo CD namespace 内の `AppProject` kind に対する権限があれば、`oc delete appproject {user} -n gitops` でリソースを削除でき、その場合 Argo CD RBAC は一切チェックされません。

この「Argo CD namespace のリソースをユーザーに触らせられない」という点は、UI/CLI の命令的な管理ではなく、宣言的に Applications を管理させたい場合に課題になります。
ですが Argo CD にはこの課題を解決する仕組みがあり、次のモジュールで確認します。

=== Apps in Any Namespace

Cluster と Shared の GitOps インスタンスで、微妙な違いに気づいたかもしれません。
Shared インスタンスでは Application 名に namespace がプレフィックスとして付いているのに対し、Cluster 側の Applications はそうなっていません。

次のコマンドをもう一度実行します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
argocd app list
----

以下の出力が表示され、Application 名が `<Namespace>/<Application Name>` 形式の2要素で構成されていることがわかります。

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
NAME                    CLUSTER     NAMESPACE   PROJECT  STATUS  HEALTH   SYNCPOLICY  CONDITIONS  REPO                                                        PATH                              TARGET
{user}-argocd/dev-tools  in-cluster  {user}-cicd  {user}    Synced  Healthy  Auto        <none>      https://github.com/AdvancedDevSecOpsWorkshop/bootstrap.git  infra/dev-tools/overlays/default  HEAD
----

これは link:https://argo-cd.readthedocs.io/en/stable/operator-manual/app-any-namespace[Apps in Any Namespace,window=’_blank’] 機能を使っているためです。
従来、Argo CD は Application リソースが Argo CD インストールと同一 namespace に存在することを要求します。
Apps in Any Namespace を使うと、Applications を別の namespace に置けるようになり、マルチテナント Argo CD インスタンスでチームごとの Applications を分離する仕組みを提供します。

この機能は、すべての Applications を同一 namespace に置く場合の重要な制約を解消します。
もしユーザーに Application リソースを宣言的に管理させてしまうと、Kubernetes API (例：oc apply、oc edit) で Application を作成・変更するだけで、
任意の Project を割り当てられてしまい、Argo CD Projects が提供するセキュリティを容易に回避できてしまいます。
これは、Argo CD RBAC が UI/CLI 経由でしか適用されず、Kubernetes 側では適用されないために起きる問題です。

Apps in Any Namespace はこの問題を避けるため、Platform チームが「Applications が存在する namespace」と「紐づく Argo CD Project」を固定でバインドすることを要求します。
本ワークショップでは、`user1-argocd` namespace は Project `user1` に、`user2-argocd` namespace は `user2` に… というように自動でバインドされます。

Application 名に namespace が含まれていることは、Apps in Any Namespace が使われていることを示します。

Apps in Any Namespace を構成するには、Applications の source namespaces を許可する設定を2箇所で行う必要があります。

1つ目は Argo CD インスタンスの起動パラメータです。
OpenShift GitOps operator を使う場合、ArgoCD CR の `sourceNamespaces` フィールドで決まります。
次のコマンドでフィールド情報を確認できます。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc explain argocd.spec.sourceNamespaces
----

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
GROUP:      argoproj.io
KIND:       ArgoCD
VERSION:    v1beta1

FIELD: sourceNamespaces <[]string>

DESCRIPTION:
    SourceNamespaces defines the namespaces application resources are allowed to
    be created in
----

このフィールドは namespace の配列を受け取りますが、管理負荷を下げるためにワイルドカードも使用できます。
Apps in Any Namespace を使う場合、ワイルドカードに適した一貫した namespace 命名規則を採用することが強く推奨されます。

[NOTE]
この推奨の意図は、Shared インスタンスに新しいテナント／ユーザーをオンボードするたびに、このフィールドを頻繁に更新しなくて済むようにすることです。
例えば `*-gitops` のような命名規則は避けてください。
このワイルドカードは `openshift-gitops` namespace まで拾ってしまうためです。

2つ目は Argo CD Project 側での `sourceNamespaces` 設定です。
これにより、「どの namespace (= その namespace 内の Applications) が、どの Project に関連付くか」が決まります。
ユーザーがセキュリティ回避のために別 Project を選ぼうとしても、namespace X の Application は常に Project Y に紐づくよう強制できます。

現時点では Argo CD CLI は sourceNamespaces の表示をサポートしていませんが、UI では確認できます。
Argo CD UI に切り替え、「Settings > Projects」へ移動して project `{user}` を選択してください。
