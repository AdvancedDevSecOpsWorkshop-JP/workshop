= The Power of GitOps with OpenShift GitOps(60 mins)

このモジュールでは、GitOps がクラスター構成とアプリケーションのデプロイを管理するためにどのように使われるかを理解します。
本モジュールは、Argo CD についてある程度の知識があることを前提としています。

[#introduction]
== Introduction

このモジュールでは、GitOps の手法を用いて Coolstore Application をデプロイし、その後 Pipeline もデプロイします。

GitOps は、クラスター構成とアプリケーションデプロイをデプロイ／管理するためのプロセスです。
GitOps では git が “source of truth（正）” となり、GitOps エンジンである OpenShift GitOps が、git に保存されている内容とクラスターの状態を突き合わせて整合（reconcile）します。

このプロセスは双方向です。
git への変更は自動的にクラスターへ反映（reconcile）され、逆にクラスター上での直接・手動の変更も、git にある定義へ自動的に差し戻される（revert）可能性があります。

このように GitOps は、configuration drift（構成のずれ）、変更管理、監査（auditing）といった一般的な課題に対応しつつ、Kubernetes クラスターの状態（state）を強力に管理する方法を提供します。

OpenShift GitOps は、標準の OpenShift または OpenShift Platform Plus のサブスクリプションに含まれており、
upstream の link:https://argoproj.github.io/cd[Argo CD,window='_blank'] プロジェクトを用いた、フルサポートの GitOps エンジンを提供します。
Argo CD は Kubernetes 向けの代表的な GitOps エンジンで、エンジン本体に加え、包括的なユーザーインターフェースなど、GitOps 環境を管理するためのさまざまな機能を提供します。

[#deploying-application]
== Deploying Coolstore Application

このセクションでは、git リポジトリ内の manifests を使って、argocd によりアプリケーションをデプロイする基本を扱います。

以前と同じ coolstore application をデプロイしますが、今回は GitOps アプローチで実施します。

このアプリケーションは2つの namespace にデプロイします。1つは "development" 環境、もう1つは "production" 環境です。これらは後ほど DevSecOps pipeline を使って更新していきます。

=== Deploy Application with Manifests

管理対象となる manifests の集合は、Argo CD では Application と呼ばれます。
したがって、Argo CD にクラスターへ適用させるためには、link:https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/#applications[Application
CRD (CustomResourceDefinition)^] を使って Application として定義する必要があります。

それでは、このアプリケーションをデプロイするために使用する Application マニフェスト を確認し、内容を整理してみましょう。
（link:https://github.com/AdvancedDevSecOpsWorkshop/workshop/blob/main/content/modules/ROOT/examples/coolstore-gitops-dev.yaml[Application マニフェスト,window="_blank"]）

.link:https://github.com/AdvancedDevSecOpsWorkshop/workshop/blob/main/content/modules/ROOT/examples/coolstore-gitops-dev.yaml[coolstore-gitops-dev.yaml,window="_blank"]
[source,yaml,subs="+macros,attributes+"]
----
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: coolstore-app
spec:
  destination:
    namespace: $USER-dev
    name: in-cluster <1>
  project: $USER <2>
  source: <3>
    path: content/modules/ROOT/files/gitops/module-02
    repoURL: https://gitea-gitea.$SUBDOMAIN/$USER/workshop.git
    targetRevision: HEAD
  syncPolicy: <4>
    automated:
      prune: true
      selfHeal: true
----
<1> destination server は、Argo CD が稼働しているクラスターの API エンドポイントです（この例では、クラスター向けにローカル解決可能な URL を使用しています）
<2> ここでは、アプリケーションを Argo CD の `default` project（`.spec.project`）にインストールしています。
[NOTE]
Argo CD の `Project` の概念は OpenShift のものとは異なります。ここで指定しているのは Argo CD の `default` project（`.spec.project`）であり、OpenShift の default project では *ありません*。
<3> マニフェストのリポジトリと、その中で YAML が配置されているパスです。
<4> `syncPolicy` は `automated` に設定され、prune と selfHeal が有効になっています。
  Prune は Git リポジトリから削除されたリソースを自動削除します。selfHeal は、リポジトリに保存されている定義から逸脱したリソースを自動的に修正します。
  たとえば `oc` や `kubectl` で行った手動変更は自動的に “修復（heal）” されます。

OpenShift GitOps は専用の namespace {user}-argocd を監視しており、そこで *Application* タイプのリソースを作成すると、OpenShift GitOps 上にアプリケーションが作成されます。

=== Addressing Configuration Drift

アプリケーション環境に変更を加えてみましょう。
replicas を増やし、その際に OpenShift GitOps が drift をどのように扱うかを確認します。

[.console-input]
[source,bash,subs="attributes+,+macros"]

----
oc -n {user}-dev scale deploy inventory-quarkus --replicas=2
----

pod が作成され始めますが、すぐに削除されることがわかります。
これは、OpenShift GitOps が inventory-quarkus deployment の application manifest に指定されたとおり、replicas 数を 1 に自動的に戻しているためです。

Argo CD では、`Application` マニフェストの `selfHeal` プロパティを設定することで、drift を自動修正するよう構成できます。
link:#_deploy_application_with_manifests[上の例] では次のとおりです。

[.console-input]
[source,yaml,subs="attributes+,+macros"]
----
# coolstore-gitops.yaml
...
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
----

演習として、次のコマンドで application を patch し、Self-healing を無効化してみましょう。

[.console-input]
[source,bash,subs="attributes+,+macros"]
----
oc patch application/coolstore-app-dev -n {user}-argocd --type=merge -p='{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":false}}}}'
----

そのうえで、replicas を変更する操作をもう一度行います。

[.console-input]
[source,bash,subs="attributes+,+macros"]

----
oc -n {user}-dev scale deploy inventory-quarkus --replicas=2
----

Application が out-of-sync 状態として表示されることに注意してください。

image::gitops-apps/gitops-user-dev-out-of-sync.png[Out-Of-Sync]

Self Heal が有効でない場合、Argo CD UI から手動で sync できます。

* まず `SYNC` をクリック
* 次に `SYNCHRONIZE` をクリック

image::gitops-apps/coolstore-manual-sync.png[Manually Sync the application]

sync が完了すると、Argo CD UI 上でアプリケーションは `in sync` と表示されます。


[#applicationsets]
== ApplicationSets

前のセクションでは、`coolstore-app` の development 版と production 版を、個別の Applications としてデプロイしました。
しかし、以前行ったように、同じ Application を少しずつ変化させた複数バージョンとしてデプロイ／生成したい場面はよくあります。

そこで登場するのが、Argo CD の link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset[ApplicationSet,window="_blank"] 機能です。
ApplicationSet を使うと、テンプレート化によって Application リソースを生成できます。
各 ApplicationSet は、1つ以上の generator を含められ、これらが Application の作成を駆動します。
Argo CD にはさまざまな generator が用意されており、Plugin アーキテクチャを通じてカスタム generator を作成することもできます。

利用可能な link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators[generators,window="_blank"] にはいくつか種類があり、代表例は次のとおりです。

* link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-List[List,window="_blank"] generator を使い、環境ごとのアプリケーションを生成する（この後すぐ例を見ます）
* link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Git/[Git,window="_blank"] generator を使い、git リポジトリの内容に基づいて Application を作成する（Module 4 で、環境向けアプリをより動的に生成する方法として扱います）
* https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Pull-Request/[Pull Request,window="_blank"] generator を使い、マージ前の自動テストのために、その場で新しい環境をプロビジョニングする
* link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Cluster/[Cluster,window="_blank"] generator を使い、複数クラスターにまたがって Application をプロビジョニングする
* link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Matrix[Matrix,window="_blank"] と link:https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Merge[Merge,window="_blank"] generator を使い、複数 generator の結果を組み合わせる

それでは、List generator を使って、先ほどデプロイした `coolstore-app` の development／production 向け Applications を作成するシンプルな例を見てみましょう。

次のコマンドで ApplicationSet をデプロイします。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
sed 's/$USER/{user}/' ~/workshop/content/modules/ROOT/examples/coolstore-gitops-appset.yaml | sed 's/$SUBDOMAIN/{subdomain}/' | oc apply -f - -n {user}-argocd
----

続いて、デプロイされた ApplicationSet を確認します。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get appset coolstore-apps -o yaml -n {user}-argocd | oc neat
----

[.console-output]
[source,yaml,subs="attributes+,+macros"]
----
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: coolstore-apps
  namespace: {user}-argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io <1>
spec:
  generators:
  - list: <2>
      elements:
      - environment: dev <3>
      - environment: prod
  goTemplate: true
  goTemplateOptions:
  - missingkey=error
  template: <4>
    metadata:
      name: coolstore-app-{{.environment}} <5>
      namespace: {user}-argocd
    spec:
      destination:
        name: in-cluster
        namespace: {user}-{{.environment}}
      project: {user}
      source:
        path: content/modules/ROOT/files/gitops/module-02
        repoURL: https://gitea-gitea.{subdomain}/{user}/workshop.git
        targetRevision: HEAD
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
----
<1> ApplicationSet が削除されたとき、Argo CD は Applications も自動的に削除します。finalizer を含めることで、Application がデプロイしたリソースも削除されるようにします。詳細は link:https://argo-cd.readthedocs.io/en/stable/user-guide/app_deletion/#about-the-deletion-finalizer[こちら,window="_blank"] を参照してください。
<2> `list` generator を使用しています。これにより、静的な要素リストを与えて動的に Application を生成できます（基本的には element 1つにつき Application 1つの 1:1 です）。
<3> 各 element は `environment` という1つの値を持ち、生成される Application オブジェクトにテンプレートとして埋め込まれます。
<4> `template` セクションで、ApplicationSet が作成する Application リソースを定義します。
<5> `environment` 値を参照して name をテンプレート化している例です。

なお、これらの Applications は先ほど手動で作成しましたが、ApplicationSet は以降それらの所有権（ownership）を引き継ぎます。
次のコマンドで確認できます。

[.console-input]
[source,sh,subs="attributes",role=execute]
----
oc get app coolstore-app-dev -o=jsonpath='{.metadata.ownerReferences}' -n {user}-argocd | jq -s .
----

[.console-output]
[source,yaml,subs="attributes+,+macros"]
----
[
  [
    {
      "apiVersion": "argoproj.io/v1alpha1",
      "blockOwnerDeletion": true,
      "controller": true,
      "kind": "ApplicationSet",
      "name": "coolstore-apps",
      "uid": "1cb40de5-09a0-440e-a12e-28941e9c81b1"
    }
  ]
]
----

このように ApplicationSets は、静的に Application オブジェクトを生成できるだけでなく、より重要なのは Module 4 で見るように、動的に生成できる点です。

[#helm]
== Helm
include::_attributes.adoc[]

link:https://helm.sh/[Helm,window="_blank"] は、Kubernetes でコンテナ化アプリケーションのパッケージ化とデプロイを標準化・簡素化する、パッケージ／インストール管理ツールです。
パッチ適用アプローチの Kustomize と異なり、Helm はテンプレート化を用いて、必要に応じてデプロイされる manifests を調整できるようにします。

[#exploring-helm]
=== Exploring Helm

Helm の基本的な考え方は次のとおりです。

* Kubernetes 向けのパッケージマネージャーで、アプリケーションを chart としてパッケージ化する
* テンプレートを用いて、インストールごとにアプリケーションを設定できるようにする
* chart のパラメーターは `values.yaml` ファイルに保持され、テンプレートから参照される

image::gitops-apps/helm-logo.png[Helm Logo]

[#exploring-helm-cli]
=== Exploring the Helm CLI

前のラボでの Kustomize と同様に、`helm` CLI はラボ環境セットアップの一部としてインストールされているはずです。
インストール済みであることを確認します。

[.console-input]
[source,bash,subs="attributes+,+macros"]
----
helm version --short
----

バージョンが表示されます。例としては次のような形式になります。

[.console-output]
[source,bash,subs="attributes+,+macros"]
----
{v3.14.4+37.el9+g7163c12}
----

Helm は、Kubernetes クラスターに Helm chart をインストールするために使用でき、インストール後はアップグレードやアンインストールなど、アプリケーションのライフサイクルを管理できます。
一方で Helm は、クラスターにインストールせずに、chart を純粋な yaml としてレンダリングすることもできます。

Helm Charts は、Kubernetes 向けにアプリケーションを定義する manifests の集合です。

Argo CD は「manifests を管理する」という思想に従っているため、Helm とは、Helm によって chart をテンプレート化（レンダリング）させる形で連携します。
つまり、Argo CD 自体は Kubernetes クラスターに chart をインストールしません。
Argo CD における Helm chart のライフサイクルは、Argo CD が使用する chart のバージョンを更新し、Argo CD が新しいバージョンをレンダリングすることで管理されます。

そのため、本ワークショップでは `helm install` ではなく、`helm template` コマンドに焦点を当てます。

この chart は、以前扱ったアプリケーションで利用する devsecops pipeline をデプロイするために使用します。
クローンしたリポジトリ内の `content/modules/ROOT/files/gitops/helm/globex-ui` ディレクトリにある chart を扱います。

それぞれをもう少し詳しく見ていきましょう。

.link:https://github.com/AdvancedDevSecOpsWorkshop/workshop/blob/main/content/modules/ROOT/files/gitops/helm/globex-ui/Chart.yaml[Chart.yaml,window='_blank']
[source,yaml,subs="+macros,attributes+"]
----
include::ROOT:example$globex-ui/Chart.yaml[]
----

このファイルは link:https://helm.sh/docs/topics/charts/#the-chartyaml-file[chart definition,window="_blank"] であり、chart の名前、バージョン、その他の特性を定義します。

.link:https://github.com/AdvancedDevSecOpsWorkshop/workshop/blob/main/content/modules/ROOT/files/gitops/helm/globex-ui/values.yaml[values.yaml,window='_blank']
[source,yaml,subs="+macros,attributes+"]
----
include::ROOT:example$globex-ui/values.yaml[]

`values.yaml` は、chart が使用するデフォルト値のセットです。chart をテンプレート化またはインストールする際に、独自の values.yaml を渡して、特定のユースケースに合わせてデフォルト値の一部または全部を上書きできます。

これは yaml ファイルであるため、`gitea` セクションのように、関連するパラメーターをまとめるために階層構造にできる点にも注目してください。

templates/ ディレクトリにはテンプレートファイルが置かれます。
Helm が chart を評価する際、templates/ 配下のすべてのファイルをテンプレートレンダリングエンジンで処理します。
その結果が収集され、Kubernetes へ渡されます。
テンプレート化の詳細は link:https://helm.sh/docs/chart_template_guide/getting_started/[こちら,window='_blank'] を参照してください。

[#helm-template]
=== Helm Template

このセクションでは、`helm template` コマンドを使って Helm chart から Kubernetes manifests を生成する方法を確認します。
このコマンドは、Helm chart の動作や、作成されるリソースを可視化するための基本ツールです。

==== Step 1: Run the Helm template Command

[#custom-values-files]
=== Custom values files

このセクションでは、Helm charts に対してカスタム values ファイルを使う方法を確認します。
これにより、chart 自体を直接変更することなく、特定の要件に合わせてデプロイ内容を調整できます。
カスタム values ファイルは、デフォルト設定を上書きする柔軟性を提供します。

==== Explore the Custom Values Configuration

"pipeline-helm-app-custom.yaml" という YAML ファイルを確認します。
このファイルは先ほどの設定に非常に似ていますが、重要な違いがあります。
それは、Helm chart と同じ Git リポジトリに保存されているカスタム values ファイルを参照している点です。

[.console-input]
[source,bash,subs="attributes+,+macros"]
----
cat ~/workshop/content/modules/ROOT/examples/pipeline-helm-app-custom.yaml
----

この YAML の中に、カスタム values ファイルの名前とパスを定義するセクションがあります。
これが Helm chart のデフォルト設定を調整する役割を担います。

[.console-output]
[source,yaml,subs="attributes+,+macros"]
----

    helm:
      valueFiles:
        - custom_values_1/values.yaml
----

ArgoCD でカスタム values ファイル付きの Helm chart をデプロイすると、chart を直接変更することなく、デフォルト設定を調整・上書きできるという利点があります。
この柔軟性により、異なる環境や特定ユースケースに合わせた別々の構成で chart をデプロイできます。

[NOTE]
すでに Pipelines の Helm chart をデプロイ済みのため、ここではカスタム values の Application はデプロイしません。2つの Applications が同じリソースを取り合って競合してしまうためです。

=== Argo CD Application with Parameter Values

このセクションでは、parameter values を Application に直接埋め込み、別の values ファイルを不要にする構成を確認します。

"pipeline-helm-app-para.yaml" という YAML ファイルを確認します。
このファイルは前の設定と同様に、Helm chart をデプロイするための Argo CD Application を定義していますが、大きな違いとして、必要な parameter values をすべて YAML 内に直接記載しています。

[.console-input]
[source,bash,subs="attributes+,+macros"]
----
cat ~/workshop/content/modules/ROOT/examples/pipeline-helm-app-para.yaml
----

.link:https://github.com/OpenShiftDemos/openshift-gitops-workshop/blob/main/content/modules/ROOT/examples/bgd-app-helm-para.yaml[bgd-app-helm-para.yaml,window='_blank']
[source,yaml,subs="+macros,attributes+"]
----

YAML の 'parameters' セクションを見ると、chart に渡したい値がすべて直接含まれていることが確認できます。

ArgoCD を通じて parameter を埋め込んだ形で Helm chart をデプロイすれば、chart 自体を変更したり外部 values ファイルに依存したりすることなく、デフォルト設定をカスタマイズできます。
これにより、環境間での設定管理を中央集約できます。

[#helm-conclusion]
=== Conclusion: Helm on ArgoCD

このモジュールでは、Argo CD を使って Helm charts をデプロイする方法を学び、また Argo CD で Helm chart にパラメータを渡すさまざまな方法を確認しました。
ここで扱ったアプローチの Pros / Cons を簡単にまとめると以下のとおりです。

|===
|*Custom Values File - Pros* | *Built-in Parameters - Pros*
|設定のカスタマイズ: 環境ごとに別の values.yaml を用意し、異なる環境向けに設定を調整できる。chart の values.yaml のデフォルト値を、必要な設定で上書きできる。|環境ごとの YAML 管理: ブランチやタグを用いて、環境ごとの YAML 構成を管理できる。
|迅速な変更: 外部 values ファイルは、個別の values を持つ複数の Helm chart を管理するよりも有利。1つのファイル変更で複数の値を素早く変更できる。|外部 values ファイルに依存しないため、`helm template` や `helm lint` を使ったローカルテスト／デバッグが容易。
|*Custom Values File - Cons*|*Built-in Parameters - Cons*
|手動更新: values ファイルの手動更新が必要となり、デフォルトの Helm charts の振る舞いから外れる。|カスタマイズの制約: YAML ファイル上の制約により、カスタマイズの自由度が限定される。
|values ファイルと chart の設定が一致しない場合、エラーや不整合が発生する可能性がある。|環境ごとに別 chart が必要となり、冗長になりうる。
|===

Argo CD で Helm charts をデプロイするパターンについては link:https://developers.redhat.com/articles/2023/05/25/3-patterns-deploying-helm-charts-argocd[こちら,window='_blank'] で詳しく読めます。

まとめとして、このモジュールではテンプレート化機能を備えた Kubernetes のパッケージマネージャーとして Helm を紹介しました。
また、ArgoCD 上での利用方法として、Helm chart を純粋な YAML としてレンダリングすることに焦点を当て、カスタム values と parameter values による柔軟な構成管理を確認しました。
このアプローチにより、Helm chart を直接変更することなくデプロイを効率化し、環境や要件に合わせた構成を実現できます。
